# Validation HEXAGONE 0.20.0

23 novembre 2026. Client et API 0.20.0.

- 144 tests unitaires/API réussis. La radio Opération est accordée à tous les membres d’une escouade inscrite dans une opération active, quel que soit leur grade. Les opérations ont des salles et jetons distincts. L’accueil, les visites admin et les déplacements vocaux temporaires ne changent pas l’inscription de l’escouade. Quitter ou terminer une opération retire la radio ; les membres restants utilisent une nouvelle salle lorsque la composition autorisée change.
- Essai avec trois clients Windows isolés et deux opérations locales : audio reçu dans la bonne opération, silence pour l’autre, émission par un membre ordinaire, changement d’opération et retrait de la radio sans déconnecter le vocal principal. Le réseau des leaders conserve ses droits existants. L’overlay affiche le leader étranger sous le libellé de son salon réel, puis retire ce groupe à la fin de sa transmission. Les noms et photos du salon local restent en place.
- Même essai sur le véritable exécutable final : bouton de squad connecté utilisable, survol rouge et déconnexion/reconnexion ; création de deux escouades supplémentaires sans quitter sa squad ; édition et ouverture par clic droit ; ordre personnel des vocaux conservé après navigation ; cartes déplacées vers une opération puis vers une autre ; refus des mêmes actions pour un non-admin. Le premier joueur inscrit devient chef d’une escouade préparée. La déconnexion du compte est vérifiée dans Mon compte et absente de la barre latérale.
- Les escouades vides gardent leurs places et un chef nul. Une escouade occupée doit toujours avoir un chef membre. Le dernier joueur peut quitter une composition vide sans la supprimer. Les créations des anciens clients, sans option `join`, conservent leur comportement précédent.
- Le déplacement vers une opération utilise une action atomique réservée aux admins. Il ne modifie ni les postes ni les joueurs, et retire les inscriptions de briefing de l’opération précédente. L’ordre de la barre latérale est personnel, enregistré par compte et serveur, sans réordonner les données de la team ; il s’applique à l’intérieur de chaque catégorie.
- Tests de l’overlay 0.19 et de l’amplification 300 % conservés, ainsi que les scénarios de connexion avec identifiants de périphériques obsolètes et erreurs vides. Les fenêtres sont sur l’écran droit, les profils sont séparés et les pistes sont simulées ; aucune création de compte fictif en production, aucune touche native injectée. Le glisser-déposer est exercé dans le navigateur de l’app et par événements DOM pour le scénario entre deux sections hors écran.
- Les descriptions demandées sont supprimées et les libellés Push To Talk / Opération sont contrôlés dans l’interface. Une invitation lisible est testée dans l’API et dans la fenêtre réservée aux admins. Le code de production reste une configuration privée du VPS, sans modifier les comptes existants.

Le candidat serveur est validé en lecture seule sur les comptes existants avant activation. Le déploiement conserve les données, les sessions et LiveKit ; seule l’API UMBRA est redémarrée. Sauvegarde avant activation : `/var/backups/umbra/pre-0.20.0-20261123-server/`, comprenant les données et la configuration. Le changement de périmètre radio s’applique côté serveur, y compris aux anciens clients. Les nouveaux outils nécessitent la mise à jour du client. Une base contenant des escouades vides doit être lue avec le nouveau modèle ; ne pas restaurer simplement un ancien serveur qui imposait un chef à chaque escouade.

La publication conserve les flux signés directs sur les deux sous-domaines, la clé de mise à jour et les identifiants d’installation/stockage. Aucun test en match Wardogs ni de charge à 40 clients n’est revendiqué.
